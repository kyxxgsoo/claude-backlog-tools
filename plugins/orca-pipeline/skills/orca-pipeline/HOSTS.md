# 현재 세션을 조율자로 사용하기

파이프라인을 시작하거나 다른 세션에서 이어받을 때 읽는다. **조율자는 사용자가 요청한 현재 세션**이다. Codex와 Claude가 같은 SKILL.md·TEMPLATES.md·프로젝트 설정을 읽으며, 아래 도구 사용법만 달라진다. 기존 프로젝트 설정에 §조율자가 없으면 이 기본값을 적용한다.

## 역할과 도구

| 책임 | Codex 호스트 | Claude Code 호스트 |
|---|---|---|
| 결정·관문·보고·Orca 받은편지함 | 현재 Codex 세션 | 현재 Claude 세션 |
| 기획·교차 검증·구현·차이 리뷰 | Orca CLI의 `worker-start` | Orca CLI의 `worker-start` |
| 구현 커밋·출시의 git 담당 | 제공된 `spawn_agent`/후속 작업 도구와 프로젝트의 git 담당 역할·지시서 | 제공된 `Agent` 도구와 프로젝트의 git 담당 역할·지시서 |
| 긴 명령·대기 | 실행 도구가 반환한 세션 ID로 출력·종료 확인. `exec_command`/`write_stdin`이 있으면 사용 | Bash의 `run_in_background`와 해당 작업 결과 도구가 있으면 사용 |

- 위 이름은 해당 도구가 세션에 실제로 제공될 때만 사용한다. 없는 도구를 호출하거나 다른 호스트의 인자를 그대로 전달하지 않는다. Codex의 `functions.exec` 안에서 호출할 수 없는 협업 도구는 직접 호출한다.
- 구현자가 커밋을 맡길 때는 **구현 작업자의 실제 호스트**를 기준으로 git 담당을 고른다. Codex 조율자 아래 Claude 구현자라면 구현 커밋은 Claude의 Agent, 출시는 Codex의 서브에이전트 도구를 쓴다.
- git 담당에는 저장소 경로, 소유 범위, 리뷰한 HEAD, 프로젝트 지시서, 금지 사항, 수락 기준을 전달한다. 이름만 같은 역할이 없으면 일반 서브에이전트에 실제 git 지시서를 전달하되, 프로젝트가 허용하는 경로여야 한다. 서브에이전트 도구가 없으면 출시 단계의 막힘을 보고한다. **Codex라는 이유로 git 직접 실행을 허용하지 않는다.**
- 모델은 현재 호스트에 맞는 프로젝트 값을 사용한다. 기존 설정이 Claude 별칭만 담고 있으면 Codex git 담당에는 전달하지 않고 기본값을 사용한다. 사용자가 정하지 않은 모델·effort를 새로 고르지 않는다. 조율자 자신의 공급자·모델은 바꾸지 않는다.
- 호스트의 일반 서브에이전트는 Orca 작업자를 대신하지 않는다. 실행 결과에는 실제 Run·Task·Dispatch와 구현 커밋·출시의 일반 git 서브에이전트를 구분한다.
- `run_in_background`가 없는 실행 도구에는 그 인자를 만들지 않는다. 지원되는 짧은 yield/세션 방식으로 실행하고, 반환된 핸들을 기록한다. 명령을 시작했다는 것과 완료됐다는 것을 구분한다.

## 실행 전 확인

1. 현재 세션의 호스트를 확인한다. 설치 폴더 이름이나 작업자 모델로 추정하지 않는다.
2. 사용할 Orca 실행 파일을 한 번 정한다. `ORCA_CLI_COMMAND`가 있으면 그 값, `ORCA_DEV_REPO_ROOT`를 노출한 개발 세션이면 `orca-dev`, 그 외 Linux의 Orca 밖에서는 `orca-ide`, 나머지는 `orca`다. `skills get orchestration`을 그 실행 파일로 읽고 이후 같은 실행 파일을 사용한다. 보조 스크립트의 `ORCA_BIN`도 같은 값으로 지정한다.
3. `status --json`과 `orchestration run-current --json`으로 현재 세션의 발신자·기존 Run 바인딩을 확인한다. Run이 아직 없는 것과 발신자가 없는 것을 구분한다. CLI가 반환한 실제 오류 코드와 안내를 따른다.
4. **자기 발신자가 확인되었을 때만** Run을 생성하거나 기존 Run을 사용한다. `no_active_sender_terminal`이면 아직 실행할 수 없다. 스킬 설치만으로 Codex 데스크톱 채팅이 Orca 터미널로 등록되지는 않는다. 지원되는 자기 세션 연결이 없다면 Orca 안에서 같은 공급자의 세션을 열어 인계해야 한다. 현재 세션을 다른 공급자로 몰래 바꾸지 않는다.
5. `--from`/`--terminal`은 현재 세션 소유임이 확인된 Orca 핸들에만 쓴다. 다른 창의 핸들을 가져오거나 임의 환경 변수를 만들어 발신자를 사칭하지 않는다. `check`는 `--terminal`이고 `--from`을 받지 않는다. 바인딩이 없을 때 일반 서브에이전트를 띄워 Orca 실행을 대신하지 않는다.

발신자 확인 실패 상태에서도 설정·지시서를 준비할 수 있다. 보고는 「준비됨, Orca 실행 전」으로 하고 실제 Run을 만들었다고 쓰지 않는다.

## 프로젝트 설정과 권한

- 사용자가 지정한 프로젝트 파일 하나를 공유한다. 지정이 없으면 기존 `.claude/orca-pipeline.md`를 읽고, 없으면 템플릿을 저장소 규칙에 맞춰 채운다. `.claude/`라는 경로가 조율자를 Claude로 고정하지 않는다.
- §머지 주체·§위임·금지 구역은 호스트가 바뀌어도 유지한다. 이미 받은 사용자 승인은 함께 기록해 반복해서 묻지 않는다. 새 범위의 행동까지 승인된 것으로 넓히지 않는다.
- 작업자 한도 대체는 작업자의 공급자만 바꾼다. 조율자는 현재 세션에 남는다. 프로젝트에 더 엄격한 한도 판정 규칙이 있으면 따른다. 예를 들어 구조화된 `usage_limit_exceeded`만 인정하는 프로젝트에서는 화면 문구 감시를 끄고(`ORCA_PIPE_LIMITWATCH=0`) 지정된 판정·대체 도구를 쓴다.

## 다른 세션에서 이어받기

`TEMPLATES.md` §9의 인계 파일에 이전 조율자·Orca 핸들·Run·공유 프로젝트 설정·단계·작업자 Dispatch·승인 내역·대기 프로세스 핸들을 남긴다.

1. **이전 조율자가 더 이상 소비하지 않는 것을 확인한다.** 해당 Run의 drain-loop와 waitreal을 종료하거나 자연 종료를 기다린다. `drain.stop` 파일을 만든 것만으로 종료됐다고 보지 않는다. 관련 없는 루프·작업자는 멈추지 않는다.
2. 새 세션의 자기 Orca 발신자로 `run-use --id <run>`을 실행하고 `run-current`의 바인딩을 확인한다. 기존 소유권 때문에 거절되면 그 오류와 현재 CLI의 인계 안내를 따른다. `--takeover-legacy`는 일반 호스트 전환용이 아니며, 실제 legacy 복구 조건일 때만 안내서를 읽고 사용한다.
3. 바인딩이 확인되지 않으면 읽기 전용 상태 확인까지만 한다. 받은편지함 ack·작업자 재시작·새 Run으로 같은 편집을 중복 실행하지 않는다.
4. 성공하면 기존 Task·Dispatch·worktree를 그대로 사용하고 밀린 배달을 처리한 다음 새 소비 루프를 시작한다. 런마다 소비자는 하나다. 공급자가 바뀌었다고 이전 작업자를 다시 띄우지 않는다.

전환 전 작업자의 활성 Dispatch가 작업의 권한이고, 새 조율자는 그 기록을 이어서 관리한다. 터미널 제목·옛 파일에 있는 ID는 권한 증거가 아니다.
